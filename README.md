# PII false-positive reduction POC (Go)

A proof of concept for cutting false positives in a regex + checksum + keyword PII
detector for **Indian identifiers**, under a **never-lose-true-PII** policy, with
everything running **locally on CPU** (servers and endpoint agents, no external API).
It adds a *verifier* stage behind the existing detector: a transparent rule
verifier, a feature-based ML verifier with pure-Go training and inference, and the
runtime plumbing for a transformer verifier served through ONNX Runtime from Go.

* Research write-up and recommendation: [`docs/REPORT.md`](docs/REPORT.md)
* Measured numbers (regenerated by `piieval`): [`docs/RESULTS.md`](docs/RESULTS.md)
* Research notes with sources: [`docs/RESEARCH_NOTES.md`](docs/RESEARCH_NOTES.md)
* Implementation review (findings, fixes, open items): [`docs/REVIEW.md`](docs/REVIEW.md)

## 1. The problem

```
aadhar 738192045614, bank acc 509347182063
```

Both numbers are 12 digits and pass the Verhoeff check; the keyword `aadhar` is
within 60 characters of both; so the current pipeline reports **two** Aadhaar
numbers. The second is a bank account. The same mechanism misfires on UPI/IMPS
reference numbers, EPFO PPO and NPS PRAN numbers, APAAR IDs, consumer numbers,
12-digit bank accounts and mobiles written as `91XXXXXXXXXX`: a 12-digit check digit
passes ~10 % of random numbers, and files are full of random 12-digit numbers.

The fix is not a better checksum. It is to decide, per candidate, **which label
governs the value**, whether a **competing identifier's label** is the one that does,
and whether the digits look like **test data** — then to let a model weigh the long
tail of context the rules cannot enumerate.

## 2. Architecture

```
file ──► regex + checksum ──► candidates ──► context analysis ──► verifier ──► score + reason ──► policy
         pkg/pii/detect       (type, span)   pkg/pii/attrib       pkg/pii/verify            per-type threshold,
         (your current gate,                 (shared by all       Rules | Linear | ONNX     capped at 0.5, logged
          reproduced)                         verifiers)
```

* **The detector is unchanged in spirit.** Regex + checksum provides recall; nothing
  downstream can find what it misses. The 60-character keyword gate is reproduced
  exactly (keyword before or after the value, case-insensitive, or in the CSV/Excel
  column header) and can be switched off to let the model act as the gate.
* **Context analysis** (`pkg/pii/attrib`) is format-aware and computed once per
  candidate:
  * **governing label** — CSV header or SQL `INSERT` column if it carries a label;
    else the nearest label to the left with *no other value between it and the
    candidate*; else a label tightly attached on the right (`7381… (Aadhaar)`,
    `7381… is my Aadhaar`). A weak/generic word (`No.`, `card`, `uid`) immediately
    left is skipped in favour of a specific label that precedes it. For NAME and
    ADDRESS claims only name/address/generic labels can govern.
  * every other label in the window with its side, distance, separator, whether a
    line break intervenes and whether the label introduces a value of its own;
  * the nearest same-type label and the nearest competing label;
  * **number shape** — digit grouping, first digit, repeated/sequential/repeating-group
    digits (dummy detection), `91`+mobile shape, Luhn/Verhoeff flags;
  * test/sample wording nearby, line statistics, and for NAME/ADDRESS: dictionary
    hits, title prefix, address cues, PIN, the word after the span.
* **Verifiers** share one interface (`verify.Verifier`): a probability-like score and
  a human-readable reason for the log.
  * `verify.Rules` — no model; suppresses only on positive evidence (competing label
    governs, dummy digits in a test context). ~1 µs.
  * `verify.Linear` — logistic regression over ~200 k sparse string features built
    from the analysis; pure Go; ~40 µs including the explanation; 6 MB artifact.
  * `onnx.Verifier` — a transformer sequence classifier reading
    `type | key | left « value » right`, run through ONNX Runtime (`-tags onnx`).
* **Policy decides, not the model.** Thresholds are per entity type, chosen on
  held-out data to keep ≥ 99 % of baseline true positives, and **capped at 0.5**: a
  candidate the model finds more likely than not is never dropped. Suppressions are
  logged with the reason.

### Label catalogue

`pkg/pii/labels` holds ~900 phrases for 18 PII kinds **and 20 competing non-PII
identifier families** (order, transaction/RRN/UTR, invoice, AWB, customer/CIF, policy,
ticket, PRAN, PPO, APAAR, consumer number, device/IMEI, PNR, timestamp, amount, cheque,
vehicle, enrolment ID, user id, generic). Matching is token-based so `aadhaar_no`,
`aadhaarNo`, `AADHAAR NO` and OCR-mangled `Acc0unt N0` all resolve. Phrases flagged
*weak* (`uid`, `card`, `pin`, `ref`, …) still gate but are not strong evidence.

## 6. Evaluation protocol

A detection is a *(span, claimed type)*. It is a **true positive** if a labelled span
of that type covers at least half of it, otherwise a **false positive** bucketed by
what the span really was (`bank_account`, `rrn`, `ppo`, `dummy`, `no_truth`, …).
Verifiers only re-score the baseline's detections, so the two headline numbers are
**TP retention** (kept TPs / baseline TPs) and **FP reduction**; recall against all
labelled spans is reported separately, counting each labelled span once. Thresholds
are chosen on `dev`, results reported on `test`, and the golden set is scored with
the same thresholds. `piieval` also reports:

* FP reduction at several retention targets (99.9 / 99.5 / 99 / 98 / 95 %);
* a **keyword gate vs. model gate** experiment: score every regex + checksum match
  (no keyword required) and compare recall and precision with the gated baseline;
* per entity type, per data shape and per FP category breakdowns;
* µs per candidate for analysis, rules and the linear model (and ms for ONNX);
* every wrong decision on the golden set, with the model's explanation.

### The synthetic corpus

30 000 documents: prose and e-mails, forms, CSV/TSV (with ambiguous and missing
headers, quoted free-text columns), JSON (nested, numeric values, log-embedded),
`k=v` logs, code and fixtures (YAML, Python, SQL, properties, curl), OCR output with
realistic character confusions, and identity cards / passbooks. Each document has a
coherent persona. Label phrasings and sentence templates are **pooled by hash** into
train-only / dev-only / test-only / shared, so dev and test contain wordings never
seen in training. Distractors (RRN, PPO, APAAR, consumer numbers, order IDs, …) are
rendered with their own labels next to PII, and 35 % of 12-digit non-Aadhaar values
are forced to pass the Verhoeff check. Everything is seeded and deterministic.

### The golden set

`testdata/golden.txt`: 48 documents in styles the generator does not produce (bank
SMS, chat, logs where `uid` is a user id, EPFO/NPS/LPG/electricity documents, ITR
acknowledgement, GST invoice, SQL dump, test fixtures, identity cards with OCR noise,
headerless CSV, the brief's example in both orders). `go test ./pkg/pii/golden`
asserts the rules keep every true positive there and remove ≥ 80 % of false
positives.

## 7. Tier A: the feature model

`verify.Features` turns a candidate + analysis into sparse binary features: claimed
type, format, keyword-gate result, governing label (kind, side, distance bucket,
separator class, weak/OCR flags) and its conjunction with the type, nearest same-type
and competing labels, every label kind in the window by side, CSV/SQL key kinds,
label and value counts, line digit density, number shape, the three nearest tokens on
each side (plus character trigrams of the nearest ones, for OCR robustness), bag of
farther tokens, and the name/address descriptors. All of it is available in
production — no generator metadata.

`verify.Train` is logistic regression with AdaGrad SGD (lazy L2), trained on
*ungated* candidates (so the model also learns what a missing keyword means);
thresholds are chosen on *gated* dev candidates (the product's detections).

### Artifact format (`models/tier_a_lr.json`)

```json
{
 "version": "20261105T023524Z",
 "schema_version": 1,
 "trained_at": "...", "training_data": "corpus.jsonl sha256:...", "examples": 216434,
 "bias": -0.12,
 "weights": {"AADHAAR&gov=bank_account": -1.52, "...": 0.0},
 "thresholds": {"AADHAAR": 0.5, "BANK_ACCOUNT": 0.41, "...": 0.5},
 "default_threshold": 0.5,
 "notes": {"dev_tp_retention": 0.9968, "dev_fp_reduction": 0.976, "...": "..."}
}
```

`schema_version` is the version of `Features`; `verify.Load` refuses an artifact
whose schema the binary does not implement.

## 8a. Which models, and why

| tier | model | why this one |
|---|---|---|
| Rules | none | the attribution + competing-label logic is most of the win and must exist anyway as the safety floor; zero deployment cost |
| Tier A | **logistic regression over sparse context features**, trained and served in pure Go | the task is a binary decision from a 120-character window with strong, nameable signals; Saha et al. and GitHub's experience show small models are competitive here; it is explainable per decision, needs no CGO, trains in 10 s, and fits endpoints. Gradient-boosted trees would be the next step if interactions beyond the hand-written conjunctions mattered (LightGBM models run in pure Go via `leaves`). |
| Tier B | **small pretrained transformer fine-tuned as a sequence classifier** (recommended: `microsoft/MiniLM-L12-H384-uncased` 33 M, `sentence-transformers/all-MiniLM-L6-v2` 22 M, or `microsoft/deberta-v3-xsmall` 22 M backbone; int8 via ONNX Runtime) | captures paraphrase and OCR noise without feature engineering, and generalises beyond the generator's wording — the step that let GitHub's verifier beat an LLM. Served through ONNX Runtime because that is the one runtime that ships as a single `.so`/`.dll`/`.dylib` for Go, Java and .NET alike. Here only a from-scratch BERT-tiny (5.4 M) could be trained because huggingface.co is not reachable from the sandbox; the pipeline is identical for a pretrained base. |
| Names / addresses (planned) | **token-classification NER** fine-tuned from the same small encoders (PERSON, ADDRESS; optionally ORG), served through `pkg/pii/onnx` | regexes cannot find names; the gazetteer baseline is the fallback for endpoints without the ONNX runtime. Candidate open models to start from: GLiNER-small / GLiNER2-PII (zero-shot, Apache 2.0), ai4privacy ModernBERT anonymiser (MIT), or an IndicBERT/MuRIL base if Indian-language names matter later. |

Not chosen: an LLM verifier (local-only requirement, endpoint CPUs, prompt-injection exposure when reading scanned text); a from-scratch deep model as the production classifier (no pretrained knowledge, learns the generator).

## 8b. CPU and GPU

Everything in this repository runs on CPU. A GPU changes only latency/throughput of Tier B and the NER model:

| | CPU only (servers and endpoints) | with GPU (servers) |
|---|---|---|
| Rules, Tier A | identical, ~70 µs per candidate | identical (not worth offloading) |
| Tier B int8, MiniLM-6 shape | ~3–10 ms per candidate on one core; batch several sessions for throughput | sub-millisecond per candidate; batch many candidates per call |
| Tier B, BERT-base shape | ~15–50 ms per candidate: server-side, low candidate rates only | fine |
| NER over whole lines (not just candidates) | feasible on servers for a 6-layer model; on endpoints only for low volumes or a 4-layer model | comfortable |

To use a GPU: install the `onnxruntime-linux-x64-gpu` release (it contains `libonnxruntime_providers_cuda.so`), make CUDA/cuDNN available, and set `PII_ORT_EP=cuda`. On Apple Silicon `PII_ORT_EP=coreml` uses the CoreML provider. If the provider cannot be loaded the session creation fails loudly rather than silently falling back, so the operator knows which path is in use.

## 8c. Adding a new model or verifier

**Another Tier A model (same features):** train anything that reads the exported sparse features — the Go feature extractor is the contract. Export to the JSON artifact format (`weights` keyed by feature string) for a linear model, or add a loader for a tree model (`github.com/dmitryikh/leaves` reads LightGBM/XGBoost files in pure Go) that implements `verify.Verifier`.

**Another ONNX classifier (Tier B):** any sequence classifier that takes `input_ids`, `attention_mask` (optionally `token_type_ids`) and returns `logits` with 1 or 2 outputs works unchanged:

1. train/fine-tune it in `ml/train_tier_b.py` (`--base <hf id or local dir>`; the input text is produced by `pkg/pii/onnxinput`, never change one side without the other);
2. the script writes `tokenizer.json`, `model.int8.onnx`, `manifest.json` (`inputs`, `max_len`, `thresholds`, `model_file`);
3. run `go test -tags onnx ./pkg/pii/onnx` with `PII_ONNX_DIR` pointing at it, then `piibench` and `piieval -onnx`;
4. promote by the gate in section 10.

**A new kind of verifier** (e.g. NER, or an ensemble): implement

```go
type Verifier interface {
    Name() string
    Score(v *detect.DocView, c *pii.Candidate, a *attrib.Analysis) (float64, string)
}
```

and add it to the configuration list in `cmd/piieval` (and `piiscan`). The harness, thresholds, breakdowns and golden-set listing come for free. For NER, the natural shape is a *candidate generator* (it replaces `detect.nameCandidates` / `addressCandidates`) plus the existing verifiers; `pkg/pii/onnx` already handles tokenisation and sessions, a token-classification head just returns `[1, seq, labels]` instead of `[1, 2]`.

**New entity types or keywords:** add a `detect.Spec` (regex + validator) and the phrases in `labels.Phrases`; add the generator field in `pkg/pii/synth/catalog.go` so the corpus covers it; bump `verify.SchemaVersion` only if `Features` changes.

## 9. Integrating with the product

1. Keep your regex/keyword lists; drop them into `detect.Specs` and `labels.Phrases`
   (both are data). Add the *competing* identifier families — that catalogue is what
   makes suppression possible.
2. After your detector emits a candidate, build a `detect.DocView` once per file
   (tokenisation + label scan), call `attrib.Analyze(view, &cand, 60)`, then one or
   more verifiers. Pass the file format you already know (`csv`, `json`, `log`, else
   `text`) — it changes how context is read.
3. Apply `model.Threshold(type)`; log `Verdict.Reason` and the model explanation with
   every suppression; keep the rules as a floor (run both, log disagreements).
4. Store analyst decisions as labelled windows (`piiexport` shows the format) — they
   are the training data for the next version. Store windows, not documents.
5. Ship model files, not binaries: see "Model lifecycle" below.

## 10. Model lifecycle

* The model is a **data file** the binary loads at start-up or on reload; a retrained
  model is a file push through the same channel as keyword updates.
* **Versioned artifact** with manifest (version, training-data hash, dev metrics,
  thresholds, feature-schema version). Schema mismatch → refused.
* **Reproducible training**: `piigen → piitrain → piieval` in about a minute; real
  labelled windows are added as another JSONL corpus.
* **Promotion gate**: ≥ 99 % TP retention on the frozen synthetic split, the golden
  set and the real labelled set; no entity type loses more than an agreed margin.
* **Rollout**: shadow mode (score and log, do not suppress) → enable per entity type
  → tighten thresholds; rollback is the previous file. Keep the 0.5 cap and the rules
  floor in every version so a bad retrain degrades to today's behaviour.
* **Monitoring**: suppression share and score histogram per entity type.

## 10a. Bringing your own data and retraining

Retraining is a file-in, file-out operation; no code changes. Three input forms are accepted everywhere a `-corpus` flag is (`piitrain`, `piieval`, `piiexport`; the flag is repeatable, so synthetic and real data are mixed in one run):

1. **Hand-marked snippets** (`.txt`): the golden-set markup. Paste real lines, mark PII as `[[TYPE:value]]` and look-alikes as `[[-:kind:value]]`; everything unmarked counts as "not PII". Separate documents with `=== <format> <shape> <title>`. See `testdata/sample_real.txt`.
2. **Decision records** (`.jsonl`): one analyst judgement per line, straight from a review queue —
   `{"text": "<the line or snippet>", "format": "text", "value": "965147382010", "type": "AADHAAR", "decision": "fp"}`
   (`start`/`end` byte offsets instead of `value` when the same digits occur twice; `decision` is `tp` or `fp`; optional `split` and `id`). Records become *partially labelled* documents: only the judged candidate is used for training and scoring, nothing else in the snippet is assumed. A rejected AADHAAR claim says nothing about a BANK_ACCOUNT claim on the same digits, and the loader respects that. See `testdata/sample_decisions.jsonl`.
3. **Full documents** (`.jsonl` of `pii.Doc`) with byte-offset spans — what `piigen` writes; use it if you label whole files with a tool.

Suggested workflow:

```bash
# 1. measure first: real data as the test set, model unchanged
```

`-real-split` places real documents that carry no `split`: `train`, `dev`, `test`, or `hash` (80/10/10 by id). `piieval` prints a separate "Real documents" table for the real part of the evaluated split, so the synthetic numbers never hide what happens on your data. The artifact manifest records every input file with its hash.

Privacy: store the snippet around the detection (the 60-character window is enough) and the decision, not the files; strip anything else before it leaves the scanner. The whole retrain runs offline on your side.

## 11. Limitations

* Training and most evaluation data are synthetic; the golden set is a smoke test.
  Treat the numbers as "the design works with wide margins", not as guarantees;
  validate on real scans in shadow mode first.
* Names and addresses use dictionaries and patterns; a token-classification NER
  model served through the same ONNX path is the right upgrade.
* Tier B is proven as a runtime (parity, export, quantisation, latency) but was only
  trained from scratch here; a pretrained encoder is what makes it worth deploying.
* CSV, JSON keys and SQL `INSERT … VALUES` are handled as structure; fixed-width and
  PDF tables are not. English only.
